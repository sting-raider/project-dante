# Project Dante — Eval Harness

Deterministic evaluation suites for the buyer-owned agentic commerce runtime
(Razorpay AI Buildathon). Every runner executes the **real** backend modules on
the deterministic rules path (`LLM_PROVIDER=""`) — no mocks of the system under
test, no fabricated numbers. If a module isn't available, the suite reports
`NOT_RUN_YET` and exits non-zero.

## Layout

```
evals/
├── datasets/
│   ├── intent_cases.json        68 intent-compilation cases
│   ├── offer_cases.json         26 offer-evaluation scenarios (ground truth = real catalog)
│   ├── breach_cases.json        25 promise-verification pairs
│   └── money_safety_cases.json  28 adversarial money-action cases
├── runners/
│   ├── harness.py               shared matching / reporting / thresholds
│   ├── run_intent_evals.py      compiler rules path vs expected constraints
│   ├── run_offer_evals.py       real search + evaluator vs per-SKU ground truth
│   ├── run_breach_evals.py      real verifier over (promised, observed) pairs
│   ├── run_money_safety_evals.py real policy engine + gated executor
│   ├── run_injection_evals.py   prompt-injection corpus through extraction path
│   └── run_all.py               orchestrator + combined summary.json
├── reports/                     generated JSON + MD reports (gitkeep only in git)
└── README.md                    this file
```

Related fixtures: `fixtures/adversarial/injection_corpus.json` (50 payloads),
`fixtures/catalog/aster_catalog.json` (112-product fictional merchant catalog).

## Running

```bash
cd apps/api
.venv/Scripts/python.exe ../../evals/runners/run_all.py          # everything
.venv/Scripts/python.exe ../../evals/runners/run_intent_evals.py # one suite (optional limit arg)
.venv/Scripts/python.exe -m pytest tests/test_eval_harness.py -q # pytest wrapper (small subsets)
```

Exit code is `0` **iff every threshold is met**. A `NOT_RUN_YET` or `ERROR`
suite fails the gate so CI cannot silently pass on skip.

## Thresholds

| Suite | Gate | Current |
|---|---|---|
| intent | critical-constraint recall = 100% | **PASS (1.0)** |
| offer | hard-constraint violation rate = 0 | **PASS (0.0)** |
| breach | F1 ≥ 0.85 on verifier-supported keys, FP = 0 | PASS |
| money safety | unauthorized money actions = 0 | **PASS (0)** |
| injection | violations = 0, treated_as_data rate = 1.0 | **PASS** |

Current detailed results live in [`docs/EVALS.md`](../docs/EVALS.md) and
`evals/reports/summary.json` (regenerated by `run_all.py`).

## Matcher semantics

- scalars compare case-insensitively; dates as ISO strings; money as integer paise
- dataset date placeholders (`<NEXT_THURSDAY>`, `<TOMORROW>`) resolve at run time
- category values match across singular/plural and compiler↔catalog vocab
- brand may appear as a soft preference (plan §12.1) rather than a hard constraint
- offer scenarios: a case fails when a ground-truth-infeasible SKU is judged
  feasible (violation) or vice versa; wrong-but-present failing keys are advisory

## Ownership

Agent J owns `evals/**`, `fixtures/intents/*`,
`fixtures/adversarial/injection_corpus.json`, and the wrapper test
`apps/api/tests/test_eval_harness.py`. Datasets are ground truth: they do not
